# 架构

pnpm workspace，TypeScript，Node 26。依赖方向自上而下：

```
apps/desktop ─┐
apps/web ─────┼─> packages/protocol ─> packages/domain
apps/cli ─────┘
apps/daemon ──> packages/control ─> packages/adapters, packages/store, packages/protocol, packages/domain
```

## 命令的路径

1. 客户端发命令信封到 `POST /v1/commands`([接口](api.md))。
2. `Control.execute` 校验信封和 `input`,会话凭证只放行它角色允许的命令，查幂等键，在一个 SQLite 事务里调 `commands.ts` 汇总的处理函数。
3. 处理函数改状态表、写事件、往 outbox 排后续工作；事件经 `GET /v1/events` 和 `WS /v1/events/ws` 推给客户端。
4. `scheduler.ts` 按 outbox 和定时器推进：准备 worktree(`provisioning.ts`)、起回合(`session.ts`、`native-session.ts`)、送达权限回答(`approvals.ts`)、合并(`workbench-session.ts` 调 `landing.ts`)、删 worktree 和审查目录，并推进摸底与改动解读会话。

## 项目级和个人级 agent

项目级 agent 是每个项目的常驻 agent(Assistant、Triage、Ideas、Goals、自建),持 lead 会话凭证，只碰自己的项目。个人级 agent 持个人密钥，跨所有项目，只走 `personal-scope.ts` 的白名单，daemon 入口和命令入口各拦一次。下表是 `agent-scope.ts` 的 `agentScopeMarkdown()` 的输出,`tests/control/agent-scope.test.ts` 核对两边一致。

前端的 `data/workbench-sessions.ts` 查询默认在失败后清空数据；看板、trace、审查显式选择保留上次成功读到的值，并携带成功读取时间和过期状态，由 `components/ReadStatus.tsx` 呈现。事件流在线时重读中的读值不算过期，事件流断开或读取失败才算。合并预检维持默认策略。`screens/board/TaskFocus.tsx` 复用读模型中的 needs、依赖、阻塞与证据，连接主视图到具体会话面板；过期的看板和审查不授权变更操作。

`tests/acceptance/verify/` 是端到端驱动：启动隔离的 fixture daemon 和桌面 app,经 CDP 按功能清单点击并核对 daemon 状态。

`tests/eval/` 是评测运行器，量「合并进 main 的结果里通不过隐藏检查的比例」:

- `tasks/<任务名>/task.json` 是冻结任务，取自本仓库的提交历史：起点是一个提交的父提交，隐藏检查是那次提交的测试。隐藏检查的文件不存副本，`hidden_files` 只列路径，内容从原提交取。
- `lib/tasks.mjs` 读取并校验任务。
- `lib/check.mjs` 在仓库根下被忽略的 `.eval-work/` 里解出起点和原提交两棵树，各跑一次隐藏检查。
- `lib/run.mjs` 做一次运行：新仓库、新 daemon、用脚本的 lead 写一个任务的计划并派发，运行结束后在 main 的树上跑隐藏检查。
- `lib/fixture-tasks.mjs` 是 fixture 运行时上的 7 种任务行为和两个条件(只有验收命令、加一条独立检查),每个条件下合并几次、漏过几次是已知的。
- `lib/frozen-tasks.mjs` 把冻结任务接到 `lib/run.mjs`:仓库只有起点一个提交并装好依赖(产品把检出里的 `node_modules` 拷进工作树和门禁的候选树，门禁沙箱里装不了依赖),任务的验收命令就是合并时的验收，隐藏检查先叠上原提交的测试文件再跑；`reference` 适配器是 fixture 换了名字，第一个回合把 scope 里的文件写成原提交上的内容再提交，用来证明这条路不用模型也能合并并通过隐藏检查。
- `lib/report.mjs` 算漏过率和完成率的 Clopper–Pearson 区间、两个条件按任务配对的精确符号检验，写成 Markdown。

单元和集成测试只用 fixture 适配器，不调用真实模型；验收里 `mode: live` 的案例只在 `scripts/acceptance.mjs --allow-live` 下跑真实模型。`tests/tsconfig.json` 由根 `tsconfig.json` 引用,`pnpm build` 和 `pnpm typecheck` 都检查测试类型;测试按包名引 `react`、`react-dom`、`@anthropic-ai/claude-agent-sdk`,由它的 `paths` 和 `vitest.config.ts` 的 alias 指到 `apps/web`、`packages/adapters` 里的副本。

### Agent runtime diagnostics

`trace.time` uses bounded reads of the local lifecycle events and native span cache for the project's selected period or one session. `trace-time.ts` sweeps request intervals once for elapsed wall time, reports cross-category overlap separately, and computes cumulative observed operation time with nested intervals removed from their containers. It returns compact samples for navigation. It does not trigger native transcript indexing or a model call. Gate time is shown separately. On the conversation surface, `visual.draw` emits a visual item in the transcript. Structured charts use the app renderers and custom HTML stays in the existing sandbox. The conversation presentation uses the surrounding message surface, while pinned visuals use the board card.

`runtime-findings.ts` pairs indexed daemon lifecycle events and cached native tool intervals. `runtime-review.ts` freezes a bounded projection for a separate read-only analysis session. Its credential only exposes paged evidence and structured report submission. Lead turns stay on the normal delivery path and `project.read` includes at most three user-shared conclusions. User-recorded experiment outcomes can produce a draft in the existing memory workflow.

`apps/daemon/src/runtime-otel.ts` tails committed lifecycle events to an opt-in OTLP HTTP/JSON log exporter. UI reads and scheduling use the local event database. The exporter batches, times out and backs off independently of the scheduler.

A runtime review skill and the Trace action share the evidence review contract in `packages/control/src/runtime-review.ts`. Approval decisions and runtime confirmation are paired separately. Native-only coverage and inferred parent links remain visible in the evidence. Optional runtime diagnostics degrade independently of Lead message delivery and task retrospective recording.
